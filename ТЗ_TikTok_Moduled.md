# TikTok Moduled — большое техническое задание

Версия документа: 1.0 — проект требований.  
Дата: 27 ноября 2026 года.  
Самостоятельное Android-приложение: **TModules**.  
Название всего проекта: **TikTok Moduled**.

Документ описывает целевую систему, а не объявляет перечисленные функции уже готовыми. Статус существующего прототипа приведён отдельно. Изменение исходников и исправление стартового сбоя не входят в результат подготовки этого документа.

## 1. Назначение и основные принципы

TikTok Moduled — модульная платформа для изменения поведения TikTok на Android. TModules объединяет патчер APK, основной менеджер модулей, текстовый редактор конфигов, каталог модулей, диагностику и управление доступами в пределах реально доступных механизмов Android.

Пользователь выбирает собственный поддерживаемый APK или комплект split APK TikTok. Патчер встраивает загрузчик и необходимые компоненты, формирует подписанный установочный результат. При запуске модифицированного TikTok загрузчик подключает выбранные пользователем DEX-модули.

Основные принципы:

1. Максимальная свобода доверенного кода модулей, без искусственного белого списка классов и методов SDK.
2. Минимальное ядро: функции изменения TikTok по возможности оформляются отдельными модулями.
3. Основной менеджер всегда находится в TModules, а не зависит от работоспособности TikTok.
4. Смена региона — отдельный комплектный модуль, не часть ядра.
5. Менеджер внутри TikTok — отдельный необязательный модуль, выбираемый тумблером в патчере.
6. Весь собственный интерфейс вне TikTok — Material Design 3, далее MD3.
7. Конфиг модуля — произвольный текстовый файл, а не форма настроек.
8. Основные сценарии работают без root и Shizuku; ограничения ОС показываются честно.
9. Нет сетевой зависимости при запуске загрузчика.
10. Безопасное восстановление важнее автоматического повторения неудачного запуска.
11. Ни сборка APK, ни наличие интерфейса не заменяют проверку на устройстве.

### 1.1. Обозначения требований

- **ОБЯЗАТЕЛЬНО** — необходимо для приёмки соответствующего этапа.
- **ПЛАН** — целевая функция, реализация которой не подтверждена.
- **РАСШИРЕНИЕ** — необязательный последующий этап, не условие первой рабочей версии.
- **ПРОТОТИП** — имеется код или артефакт, но не обязательно проверено выполнение на устройстве.

Все новые поля форматов, лимиты и численные бюджеты ниже являются проектными решениями этого ТЗ, если прямо не отмечены как существующее поведение. Они подлежат реализации и проверке, а не считаются уже действующим контрактом.

## 2. Текущее состояние и блокирующие проблемы

### 2.1. Что существует в рабочем проекте

- Разделение на `core`, `module-api`, `runtime`, `manager`, `demo-host`, `sample-module`, `standalone-ui`, `site`.
- Установка локального ZIP-модуля, переключение состояния, удаление с сохранением конфига.
- Редактор текстового конфига UTF-8 с лимитом 1 MiB.
- DEX-загрузчик и API доступа к контексту, ClassLoader, данным, конфигу, Java-хукам и логам.
- Java/ART-hook backend Pine core 0.3.0.
- Подпись-защищённый мост менеджера и хоста, локальные снимки модулей.
- Начальная аварийная защита: три подтверждённых сбоя за десять минут, затем защёлкивающийся safe mode.
- Тестовый хост и пример модуля для перехвата его метода.
- MD3-компоненты и темы самостоятельных APK; UI-зависимости отделены от runtime.
- Исходник статического MD3-каталога для GitHub Pages.

По отчёту последней сборки версия APK — `0.2.0-md3`, `versionCode 2`; сборка успешна, пройдены 13 проверок ядра и статические проверки. Это не доказательство успешного выполнения сценариев Android.

### 2.2. Блокирующий дефект B-001

**Пользователь сообщил, что TModules падает при старте. Причина не установлена.**

Нет подтверждённого stack trace и результата успешного повторного запуска после исправления. Нельзя приписывать сбой конкретной теме, библиотеке или строке кода без диагностики. Работоспособность текущей MD3-сборки на устройстве не подтверждена.

До закрытия B-001 нельзя объявлять менеджер готовым к пользовательскому тестированию модулей. Приёмка исправления описана в разделе 24.

### 2.3. Чего в прототипе ещё нет

- Реального патчера TikTok и проверки результата на конкретном APK.
- Завершённого pipeline для split APK и подписи всего установочного комплекта.
- Версионного адаптера TikTok и комплектного модуля региона.
- Необязательного менеджера внутри TikTok.
- Подключённого Android-клиента репозиториев и обновлений.
- Подписей авторов модулей и полного управления доверием.
- Полноценной многопроцессной интеграции.
- Управления системными разрешениями TikTok.
- Автоматического копирования отчёта о сбое.
- Универсальных resource hooks, native hooks и патчинга `.so`.

Статический сайт не опубликован. Успешный запуск примера с реальным перехватом на устройстве также должен быть подтверждён отдельно.

## 4. Платформа и совместимость

### 4.1. Базовые решения прототипа

- Нативное Android-приложение, текущий язык реализации — Java.
- `minSdk 28`: Android 9 и выше как нижняя проектная граница.
- Текущие `compileSdk` и `targetSdk` — 35; это не заявление об их актуальности для будущего релиза.
- Gradle 8.11.1, Android Gradle Plugin 8.6.1 — зафиксированная существующая сборочная база.
- Material Components 1.12.0, AppCompat 1.7.0 — текущие UI-зависимости, не требование никогда их не обновлять.
- Основной первый кандидат ABI — `arm64-v8a`; окончательно подтверждается выбранным APK и hook backend.

Поддержка начинается не с обещания «Android 9+», а с опубликованного списка реально проверенных сочетаний. Поддержка установки TModules и поддержка хуков внутри TikTok учитываются отдельно.

### 4.2. Матрица поддержки

Для каждого проверенного сочетания фиксируются:

- версия Android/API, модель устройства и прошивка;
- ABI, размер страницы памяти при значимости для native-компонентов;
- package ID, `versionName`, `versionCode`, SHA-256 входного APK или набора splits;
- версия патчера, runtime, hook backend и адаптера;
- результат запуска без модулей, с тестовым модулем и с модулем региона;
- известные ограничения и дата проверки.

Статусы: «проверено», «экспериментально», «не поддерживается», «не проверено». Последний статус нельзя отображать как успешную совместимость.

## 5. Архитектура

### 5.1. Компоненты

- `core`: независимые модели, валидация архивов, хеширование, политика сбоев и тестируемая логика.
- `module-api`: минимальный контракт автора модуля без MD3-зависимостей.
- `runtime`: bootstrap, загрузка DEX, хуки, снимки, журналирование, safe mode.
- `manager`: TModules, хранилище модулей, IPC, редактор и управление состояниями.
- `standalone-ui`: общие MD3-компоненты самостоятельных приложений.
- `demo-host`: изолированный тестовый хост платформы.
- `sample-module`: пример настоящего исполняемого модуля.
- `site`: статический каталог и его метаданные.
- Будущая подсистема `patcher`: анализ APK, план изменений, сборка, подпись и проверка.
- Будущие пакеты `region-module`, `inapp-manager`: отдельные модули, не обязательные зависимости ядра.

Названия будущих каталогов рекомендательные; архитектурные границы обязательны.

### 5.2. Поток данных

1. Пользователь устанавливает модуль или меняет его конфиг в TModules.
2. Менеджер сохраняет проверенное состояние транзакционно.
3. Runtime при следующем запуске запрашивает согласованный снимок через защищённый IPC.
4. Новый снимок полностью проверяется и публикуется атомарно.
5. Runtime использует локальные файлы private storage, не исполняет DEX прямо из Downloads.
6. Проверяются safe mode, совместимость и список активных модулей.
7. В детерминированном порядке запускаются разрешённые модули.
8. Диагностика возвращается в менеджер по доступному каналу.

При недоступном менеджере допускается последний целый снимок, но UI и логи обязаны показывать его устаревание. Отключение модуля в недоступном менеджере не считается мгновенным отзывом уже скопированного кода.

## 6. Основные пользовательские сценарии

### 6.1. Первый запуск

- TModules открывается без падения и без обязательного доступа к файлам всего устройства.
- Показывает назначение платформы, риски доверенного DEX и отсутствие гарантии совместимости.
- Разделы доступны без TikTok и без интернета: патчер, модули, конфиги, диагностика, доступы.
- Пустые состояния объясняют следующий шаг, а не имитируют успешно настроенную систему.

### 6.2. Патчинг TikTok

Выбор файла → анализ → проверка совместимости → выбор комплектных модулей и изменений разрешений → просмотр плана → патчинг → проверка и подпись → сохранение результата → системная установка по подтверждению пользователя.

### 6.3. Установка модуля

Выбор ZIP или записи каталога → проверка пакета → показ автора, версии, совместимости и доверия → подтверждение → атомарная установка → предложение включить → отметка о необходимом перезапуске.

### 6.4. Работа с конфигом

Список модулей → редактор текстового файла → изменение → сохранение без преобразований → уведомление «Применится после перезапуска». При выходе с изменениями — сохранить, выйти без сохранения или отменить выход.

### 6.5. Авария

Три подтверждённых сбоя в окне → следующий запуск без пользовательских и комплектных модулей → отчёт → копирование по доступному механизму → выбор модулей для дальнейшего запуска → явный выход из safe mode.

## 7. Требования к патчеру

### 7.1. Входные данные

- APK выбирается через системный Storage Access Framework.
- Для splits пользователь выбирает комплект; формат импорта и поддерживаемые контейнеры перечисляются явно.
- Поддержка `.apks`, `.xapk` или иных контейнеров не считается автоматическим следствием поддержки APK.
- Первая реализация вправе поддерживать только один согласованный монолитный APK. Неподдерживаемый split-набор отклоняется до изменения файлов.
- Автоматическое извлечение из установленного приложения — дополнительное удобство, не обязательное условие первой версии.
- Исходные файлы не изменяются и не удаляются.

### 7.2. Предварительный анализ

**PAT-01.** Прочитать manifest, package ID, версии, SDK-ограничения, ABI и структуру DEX/native-файлов.

**PAT-02.** Сопоставить вход с поддерживаемым профилем. При несовпадении обязательных признаков остановиться с понятной причиной.

**PAT-03.** Проверить комплектность splits, общее происхождение, имена и отсутствие дубликатов. Не смешивать splits разных версий.

**PAT-04.** Проверить свободное место по оценке входа, временных файлов и выхода; показать оценку до запуска.

**PAT-05.** Показать полный план: bootstrap, компоненты IPC, разрешения, подпись, опциональные модули и возможные ограничения установки.

### 7.3. Изменения APK

**PAT-06.** Встроить runtime и необходимые native-компоненты выбранного hook backend, исключив ненужные ABI.

**PAT-07.** Разрешить конфликты package/class/resource names детерминированно. Не включать весь интерфейс менеджера и MD3 внутрь runtime.

**PAT-08.** Точку запуска выбирать по фактическому анализу TikTok. ContentProvider прототипа не считать доказательством запуска до `Application.attachBaseContext` или до любого кода TikTok.

**PAT-09.** Если требуемый ранний хук выполняется раньше bootstrap, нужен отдельный версионный адаптер точки входа. Не заявлять перехват уже прошедшего участка.

**PAT-10.** Не ломать launcher-компоненты, authorities, существующие providers и manifest placeholders. Проверять итоговые значения и конфликты.

**PAT-11.** Повторный патч уже изменённого входа распознавать: предложить исходный APK либо поддерживаемое обновление, не дублировать bootstrap.

### 7.4. Подпись и установка

- Изменённый APK подписывается выбранным ключом; ключ сохраняется для совместимых обновлений.
- Для используемого signature-моста сертификаты TModules и изменённого хоста должны соответствовать его модели допуска.
- Обычный официальный TikTok нельзя молча обновить APK с посторонней подписью. При конфликте показать варианты и риск потери данных до запуска установки.
- Смена package ID — отдельный сложный профиль, не гарантированный способ параллельной установки.
- Выходной APK проходит проверку целостности ZIP, структуры, подписи и необходимых компонентов.
- Если поддерживается split-выход, все части подписываются согласованно и устанавливаются одной пользовательской сессией.
- Не обещать автоматическое превращение любого split-набора в универсальный APK.
- Секретный ключ не попадает в исходники, логи, публичные отчёты или пользовательскую папку с артефактами.
- Для переносимого релизного менеджера заранее выбрать модель управления ключами; debug key не является production-решением.

### 7.5. Отказоустойчивость

Работа идёт во временном каталоге. Готовый результат публикуется только после всех проверок. Ошибка или отмена не затрагивает исходный APK и предыдущий успешный результат. Очистка удаляет только собственные временные файлы. UI показывает реальный этап и причину ошибки, а не фиктивные проценты.

## 8. Загрузчик и жизненный цикл модулей

**RUN-01.** Инициализация runtime идемпотентна в пределах процесса.

**RUN-02.** До исполнения стороннего кода проверяются safe mode, целостность снимка, формат и совместимость.

**RUN-03.** При старте отсутствуют HTTP-запросы, обновление каталога и ожидание сайта.

**RUN-04.** На основном потоке нет больших операций распаковки и сети. Необходимая ранняя синхронная работа минимизируется и измеряется; её перенос не должен создавать гонку с целевыми хуками.

**RUN-05.** Отдельные ClassLoader модулей не подменяют общий API дублирующими копиями. Конфликт встроенного API обнаруживается или предотвращается упаковкой.

**RUN-06.** Порядок загрузки детерминирован. Для первой версии — стабильная сортировка по ID. Если позднее вводятся зависимости, нужны обнаружение циклов и документированный порядок.

**RUN-07.** Ошибка проверки одного пакета блокирует его исполнение и отражается в диагностике. Продолжение загрузки остальных возможно только если целостность runtime не нарушена.

**RUN-08.** Исключение после установки хуков не считается чистым откатом. Модуль отмечается ошибочным, пользователь получает требование перезапуска.

**RUN-09.** В логах различаются: установлен, выбран, скопирован в снимок, загружен, запущен, ошибка, заблокирован safe mode, несовместим.

**RUN-10.** Выключение модуля действует на следующий запуск. Уже загруженный код не объявляется выгруженным.

### 8.1. Многопроцессность

В прототипе поддерживается только основной процесс. Целевая поддержка вспомогательных процессов — отдельный этап с инвентаризацией процессов TikTok.

Для каждого процесса задаются условия bootstrap, допустимые модули, ID запуска и правила диагностики. Счётчик сбоев должен исключать повторный учёт одного exit event. Запуск модуля во всех процессах по умолчанию не допускается без явного контракта. Операции снимков защищаются от межпроцессных гонок.

## 9. API и свобода модулей

Модуль — доверенный исполняемый DEX-код в процессе хоста, а не ограниченный набор декларативных твиков.

Минимальный SDK предоставляет:

- контекст приложения хоста и его ClassLoader;
- идентификатор, версию и имя текущего процесса;
- ID и версию runtime/API;
- приватный каталог рабочих данных модуля;
- доступ на чтение к снимку текстового конфига;
- журналирование с ID модуля;
- Java/ART hook API с явным описанием результата и ошибок;
- запрос программного перезапуска;
- сведения о версии TikTok и поддерживаемом адаптере.

SDK не запрещает reflection или собственные инструменты автора. Совместимость таких инструментов и их влияние на хост остаются ответственностью автора и пользователя.

### 9.1. Хуки

- Перехват методов Java/ART — основной первый механизм, проверяемый на конкретном backend.
- Передача аргументов, изменение результата и обработка исключения должны иметь тесты.
- Семантика нескольких хуков на одном методе документируется по фактическому backend, без обещания произвольной приоритизации.
- Подмена ресурсов, native inline hooks, JNI-перехваты и патчинг файлов `.so` — разные механизмы, не синоним «есть DEX».
- Для native-расширений отдельно проверяются ABI, упаковка библиотек, время загрузки, совместимость и аварийное восстановление.

### 9.2. Совместимость API

Несовместимая версия API блокируется до вызова entrypoint. Обновление API сопровождается описанием миграции. Текущий `apiVersion: 1` не должен менять смысл без изменения контракта. Поля будущих расширений не должны молча интерпретироваться старым загрузчиком как поддержанные функции.

## 10. Формат модуля и архива

### 10.1. Поддерживаемый прототипом пакет v1

ZIP содержит ровно два файла в корне:

```text
module.json
classes.dex
```

Ресурсы, дополнительные DEX, каталоги и native-библиотеки этим форматом не поддерживаются. Они требуют новой версии формата и миграции валидатора, а не снятия проверок ради одного пакета.

Обязательные поля внутреннего `module.json`:

- `id`: постоянный уникальный ID, например `org.author.module`;
- `name`: отображаемое название;
- `description`: текстовое описание;
- `version`: человекочитаемая версия;
- `versionCode`: целое число для сравнения обновлений;
- `apiVersion`: версия контракта SDK;
- `entrypoint`: полное имя класса точки входа;
- `targetPackages`: список разрешённых package ID хоста.

Проектный лимит ID — 128 ASCII-символов, допустимы буквы нижнего регистра, цифры, точки и подчёркивания; ID не используется как путь без отдельной валидации. Итоговый валидатор обязан согласовать это правило с существующими тестовыми пакетами.

Пример внутреннего манифеста:

```json
{
  "id": "org.author.example",
  "name": "Пример модуля",
  "description": "Описание возможностей и ограничений",
  "version": "1.0.0",
  "versionCode": 1,
  "apiVersion": 1,
  "entrypoint": "org.author.example.MainModule",
  "targetPackages": ["package.id.of.supported.host"]
}
```

Это пример структуры, а не готовый пакет для TikTok. Фактический package ID определяется выбранным входным APK.

### 10.2. Авторский descriptor распространения

Удалённый descriptor включает поля внутреннего манифеста и дополнительные сведения:

- `downloadUrl`: HTTPS-ссылка на ZIP;
- `archiveSha256`: SHA-256 точных байтов ZIP;
- `iconUrl`: необязательная HTTPS-ссылка;
- `screenshots`: необязательный список HTTPS-ссылок;
- сведения об авторе и источнике, если доступны;
- в новой версии формата — сведения о доверенном ключе и отделённой подписи.

**Важное правило:** `archiveSha256` не помещается внутрь того же ZIP как хеш всего этого ZIP: это создаёт самоссылку. В архиве хранится копия манифеста исполняемого модуля; внешний descriptor добавляет транспортные поля. При скачивании сравниваются все общие значимые поля, а не побайтовое равенство JSON с разными транспортными полями.

Изменение этого контракта оформляется версией схемы. Нельзя заявлять проверку авторства на основании одного SHA-256 из того же недоверенного источника.

### 10.3. Безопасная обработка пакетов

**PKG-01.** Запрещены абсолютные пути, `..`, неоднозначные разделители, дубли имён, выход из целевого каталога и неожиданные записи.

**PKG-02.** Ограничения применяются к потоку реально распакованных байтов, а не только ZIP metadata. Повреждённый CRC, неподдерживаемый метод и шифрование приводят к отказу.

**PKG-03.** Проектные верхние границы первой версии: descriptor/manifest 256 KiB, ZIP 64 MiB, DEX 64 MiB, config 1 MiB. До принятия в код проверить реальные текущие лимиты и тесты; несовпадение документировать как миграцию.

**PKG-04.** Проверяются корректность JSON, обязательные поля, типы, дубликаты JSON-ключей, версия API и минимальная валидность DEX. Валидный заголовок DEX не доказывает безопасность кода.

**PKG-05.** Установка атомарна: staging → проверка → публикация. При ошибке сохраняется предыдущая рабочая версия и конфиг.

**PKG-06.** Установка пакета с существующим ID рассматривается как обновление/замена и требует проверки источника доверия. ID сам по себе не доказывает того же автора.

## 11. Менеджер модулей TModules

Обязательные функции:

- установка из файла без подключения к каталогу;
- поиск и установка из подключённых репозиториев;
- список установленных модулей с версиями и совместимостью;
- включение/отключение и массовое отключение;
- просмотр описания, источника, доверия и ошибок;
- открытие текстового конфига;
- обновление с подтверждением новых условий доверия;
- удаление с выбором сохранения данных; безопасное значение по умолчанию — сохранить конфиг;
- индикация ожидающего применения состояния;
- переход к диагностике и доступам;
- информация о доступности моста и возрасте снимка хоста.

Установить не означает исполнить. Новый сторонний модуль по целевому правилу устанавливается выключенным до явного согласия. Если прототип ведёт себя иначе, это отдельное изменение при реализации, а не уже выполненная гарантия.

При переключении с ошибкой сохранения UI возвращается к реально сохранённому значению без рекурсивного цикла listener. Экран не показывает успех до завершения операции хранения.

Модули региона и встроенного менеджера отображаются как обычные отдельные модули с понятной отметкой «комплектный». Удаление или отключение такого модуля не повреждает ядро.

## 12. Текстовые конфиги

**CFG-01.** У каждого модуля имеется отдельный конфиг. Текущее имя — `config.txt`, кодировка — UTF-8, лимит — 1 MiB точных байтов при сохранении.

**CFG-02.** Содержимое непрозрачно для платформы: JSON, INI, TOML, скрипт, собственный синтаксис или обычный текст. Допустим пустой файл.

**CFG-03.** Запрещены `trim()`, автоформатирование, навязывание JSON-схемы, генерация формы параметров, автоматическое добавление финального перевода строки и молчаливая замена неверного UTF-8.

**CFG-04.** Без внесённых пользователем изменений открытие/сохранение сохраняет точные байты валидного UTF-8, включая BOM при его наличии, пробелы, табы, CRLF/LF и отсутствие финального перевода строки. Если Android-редактор нормализует окончания строк, это исправляется или сохранение блокируется с объяснением; молчаливая нормализация недопустима.

**CFG-05.** Редактор использует моноширинный шрифт, отключённую автокоррекцию и удобную работу с длинными строками. Перенос строк — настройка отображения, а не изменение файла.

**CFG-06.** Сохранение атомарно. При ошибке ввода-вывода старый файл не теряется, введённый текст остаётся доступным.

**CFG-07.** Черновик переживает поворот и штатное восстановление экрана. Обработка принудительной смерти процесса тестируется отдельно; сохранение большого черновика не должно превышать лимиты saved instance state.

**CFG-08.** Несохранённые изменения нельзя потерять одним нажатием «Назад».

**CFG-09.** Применение — после перезапуска. Runtime передаёт согласованный снимок, а не частично записываемый файл.

**CFG-10.** Изменение локального снимка модулем не синхронизируется обратно автоматически. Для рабочих данных предназначен `dataDirectory()`.

**CFG-11.** Импорт/экспорт конфигов выполняется через системный выбор файла. Восстановление ранее сохранённого конфига при повторной установке того же ID показывается пользователю.

Горячая перезагрузка и двусторонняя синхронизация — расширения с отдельным контрактом согласованности. Они не должны незаметно менять модель первой версии.

## 13. Каталог, репозитории и обновления

### 13.1. Организация

GitHub Pages размещает общий статический каталог. Каталог содержит ссылки на манифесты авторов; автор хранит descriptor и архив в своём репозитории или другом допустимом HTTPS-источнике. Централизованное копирование всех архивов не требуется.

Минимальная схема каталога сохраняет текущую идею:

```json
{
  "schemaVersion": 1,
  "name": "TikTok Moduled Modules",
  "modules": [
    {
      "id": "org.author.example",
      "name": "Пример модуля",
      "description": "Краткое описание",
      "manifestUrl": "https://author.example/module.json"
    }
  ]
}
```

Адрес примера не является опубликованным репозиторием. Реальный URL каталога назначается при публикации. Веб-каталог — браузерное представление, а TModules читает машинные метаданные, не парсит HTML.

### 13.2. Поведение клиента

- Добавление, отключение и удаление источника по URL.
- Поиск по названию, ID и описанию, понятные состояния пустого результата и ошибки.
- Иконка и скриншоты необязательны; их отсутствие не мешает установке.
- Локальный кеш последнего валидного каталога с датой обновления.
- Обновление по запросу пользователя; без скрытого исполнения скачанного кода.
- Таймауты, отмена, ограничение размера и числа параллельных загрузок.
- Запрет HTTP downgrade; перенаправления перепроверяются по политике URL.
- Ссылки из JSON не исполняются как HTML/JavaScript; изображения имеют лимиты размера.
- Повторный ID из разных источников требует выбора источника и не перехватывает существующее доверие молча.
- Ошибка одного источника не уничтожает кеш и установленные модули.
- Загрузка архива во временный файл, проверка SHA-256, подписи при наличии и общих полей manifest до установки.

### 13.3. Обновления модулей

Сравнение ведётся по целому `versionCode`, а не лексикографически по `version`. Откат версии требует отдельного подтверждения. Обновление сохраняет конфиг и данные; миграция формата конфига — ответственность автора, не повод платформе переписать файл.

Обновление исполняемого модуля применяется после перезапуска. Источник, авторский ключ и требуемые возможности показываются до подтверждения. Автоматические обновления выключены в первой целевой версии. Возврат к предыдущему коду не обещает откат изменённых модулем данных.

## 14. Доверие и безопасность

### 14.1. Реальная граница защиты

DEX исполняется с возможностями процесса TikTok. Раздельный ClassLoader не создаёт отдельный UID, sandbox или надёжную защиту данных хоста. Android изолирует приложения на уровне процессов/UID; это не изоляция библиотек внутри одного процесса [S1, S2].

Перед исполнением стороннего модуля пользователь видит предупреждение: модуль потенциально способен читать доступные хосту данные, менять его поведение, обращаться к сети при наличии возможностей хоста и нарушать работу приложения.

### 14.2. Целостность и авторство

- SHA-256 нужен для проверки целостности, но не удостоверяет автора сам по себе.
- Удалённый код сохраняется в доверенное локальное хранилище до загрузки [S1].
- Для Android 14 при `targetSdk` 34+ учитывается требование read-only к динамически загружаемым файлам; порядок создания и проверки файла тестируется отдельно [S3].
- Для production-канала проектируется отделённая подпись точного артефакта и проверяемых метаданных. Алгоритм и канонический формат подписываемых данных фиксируются отдельным ADR до включения проверки.
- Первое доверие авторскому ключу подтверждается пользователем; fingerprint показывается в карточке.
- Смена ключа требует подтверждённой процедуры ротации или нового согласия, а не автоматического принятия.
- Локальный неподписанный ZIP можно установить в режиме явного доверия с предупреждением. Это не означает «проверенный автор».
- Отзыв ключа/модуля требует доставки сведений и не может гарантированно сработать у полностью офлайн-хоста.

### 14.3. Не делать ложных обещаний

Проект не позиционируется как песочница недоверенного кода. Отдельные каталоги и API-гейты полезны для организации и кооперативных модулей, но не предотвращают обход через прямые API хоста.

## 15. Доступы модулей и разрешения Android

Три разных понятия должны быть разделены в интерфейсе.

### 15.1. Декларируемые возможности модуля

Модуль может сообщать о работе с сетью, файлами, буфером, UI или перезапуском. Эти сведения помогают пользователю принять решение. Отсутствие декларации не доказывает, что DEX не использует такую возможность.

Согласие может ограничивать API, предоставляемые платформой, но экран обязан пояснять: «Не является изоляцией кода внутри TikTok». Для недоступного реального ограничения не рисуется переключатель, создающий впечатление гарантированного запрета.

### 15.2. Системные разрешения хоста

Показываются фактические разрешения и доступные действия: запрос допустимого runtime permission из хоста, переход к системным настройкам, объяснение отказа или недоступности. TModules не объявляет, что может без привилегий выдать или отозвать любое разрешение чужого UID.

Разрешения имеют разные уровни защиты; добавление записи в manifest не заменяет системную выдачу опасного разрешения и не обеспечивает signature-допуск [S4, S5].

### 15.3. Патч manifest

Патчер позволяет просмотреть и выбрать поддерживаемые изменения `uses-permission`, показать различия до/после и предупредить о последствиях. Это изменение деклараций APK, а не «выдача всех прав».

Удаление разрешения может сломать функцию TikTok. Добавление не гарантирует доступ к privileged/signature API. Все изменения включаются в отчёт патчинга и требуют повторной подписи результата.

Shizuku/root — необязательное расширение. Базовые установка модулей, конфиги, каталог, загрузка, safe mode и доступный программный рестарт от них не зависят.

## 16. Комплектный модуль региона

- Отдельный DEX-пакет со своим ID, версией, конфигом и совместимостью.
- Входит в поставку как предлагаемый модуль; не вшивается в обязательную логику ядра.
- Устанавливается/включается по явному выбору, отключается как обычный модуль.
- Настройки региона хранятся обычным текстом в формате автора; TModules не превращает их в навязанную форму.
- Какие именно сигналы TikTok изменяются, фиксируется после анализа конкретной версии.
- Проверка различает локально подменённое значение и фактический ответ сервера.
- Не обещается изменение IP, SIM, GPS, региона аккаунта и серверных ограничений одним универсальным переключателем.
- При неподдерживаемой версии модуль сообщает несовместимость, а не создаёт видимость успешной смены.

Приёмка: на согласованной версии продемонстрирован конкретный измеримый локальный эффект, отключение возвращает исходное поведение после рестарта, ограничения описаны.

## 17. Необязательный менеджер внутри TikTok

- Самостоятельный модуль, который можно добавить тумблером при патчинге.
- При выключенном тумблере пакет/точка входа менеджера не включается по скрытой зависимости.
- Включение в комплект и фактическое активное состояние модуля различаются в UI.
- Основной менеджер, установка из файлов, конфиги и восстановление остаются доступны в TModules.
- Внутренний экран не является обязательным условием загрузки других модулей.
- Действия используют тот же источник состояния и модель «после перезапуска», не создают второй несогласованный список.
- При недоступном мосте показывается read-only/ошибка синхронизации, а не ложный успех.
- В safe mode не загружается, как и остальные модули. Восстановление выполняется через независимый TModules.
- Визуальная интеграция учитывает TikTok; перенос MD3-библиотек внутрь хоста не требуется ради внешнего менеджера.

Точное место входа в TikTok определяется версионным адаптером и проверяется на устройстве.

## 18. Аварийная защита и восстановление

### 18.1. Политика сбоев

**CR-01.** «Более двух крашей» означает три подтверждённых сбоя за скользящие десять минут.

**CR-02.** После третьего сбоя следующий запуск активирует safe mode до исполнения любых модулей. Режим защёлкивается и не снимается обычным рестартом.

**CR-03.** Safe mode блокирует все пользовательские и комплектные модули, включая регион и внутренний менеджер. Минимальная часть runtime для диагностики и восстановления остаётся.

**CR-04.** Авария хоста не доказывает виновность конкретного модуля; отчёт не назначает виновного без данных.

**CR-05.** Ручной force stop, штатный выход и системное освобождение памяти не считаются подтверждёнными крашами. ANR учитывается отдельным типом и отдельной политикой, не добавляется молча в этот счётчик.

**CR-06.** На Android 11+ использовать доступные сведения `ApplicationExitInfo`, исключая повторный учёт. На Android 9–10 честно обозначить более узкое покрытие Java uncaught exceptions.

**CR-07.** Сброс — явное действие с указанием последствий; пользователь может сначала отключить подозрительные модули. Если менеджер недоступен, локальная защёлка хоста всё равно должна предотвращать повторную загрузку.

**CR-08.** Повреждение состояния защиты не интерпретируется как разрешение исполнить весь код. Применяется консервативный восстановительный режим с диагностикой.

### 18.2. Надёжность обработки

Нельзя рассчитывать, что умирающий процесс успеет открыть Activity, выполнить IPC или скопировать текст. Минимальный отчёт сохраняется локально до передачи исходному обработчику исключений. Проверяются сбои записи, нехватка места и замена uncaught handler самим хостом.

Native-сбои и ANR не покрываются обычным Java handler. Доступность системных traces зависит от версии ОС и фактического события [S6]. Текущий ограниченный base64-префикс trace не считается полноценным crash viewer.

### 18.3. Копирование краш-лога

Пользовательское требование — максимально автоматическое копирование отчёта в буфер. Целевой сценарий:

1. Сохранить отчёт независимо от буфера.
2. При следующем допустимом открытии foreground-экрана с согласием пользователя попытаться скопировать отчёт, если включена настройка автокопирования.
3. Показать факт успешного копирования либо причину недоступности.
4. Всегда оставить кнопку «Скопировать» и экспорт файла.

Настройка автокопирования включается явным согласием из-за чувствительности логов. Нельзя обещать гарантированное копирование из фонового или уже завершившегося процесса; ограничения буфера и фонового UI учитываются по ОС [S7, S8]. Длинный отчёт не обрезается без уведомления; полный вариант доступен файлом.

### 18.4. Собственные сбои TModules

Краш менеджера — отдельный контур, не тот же счётчик, что у TikTok. Требуется локальная диагностика старта TModules и доступный путь получить отчёт при неработающем основном экране. Обработчик диагностики не должен тянуть сложный MD3 UI до сохранения ошибки.

Для B-001 сначала получают реальный logcat/stack trace или иной подтверждённый отчёт. Исправление без воспроизведения и повторной проверки не закрывает дефект.

## 19. Программный перезапуск

Допускается рестарт через загрузчик без Shizuku: сохранение состояния → согласование перезапуска → допустимое планирование запуска → завершение своего процесса. Пользователь заранее предупреждается о возможной необходимости открыть TikTok вручную.

Ограничения:

- Это не системный Force stop и не гарантированная остановка всех процессов.
- Фоновый запуск Activity и точность AlarmManager ограничиваются ОС [S8, S9].
- Перезапуск не должен создавать бесконечный цикл, сбрасывать счётчик сбоев или обходить safe mode.
- При невозможности автоматического запуска показывается простая инструкция ручного запуска.
- Запрос перезапуска модулем журналируется; частые запросы ограничиваются платформенным API, но это не sandbox для произвольного DEX.

Полный контролируемый рестарт нескольких процессов — отдельный этап с проверяемым покрытием.

## 20. IPC, хранение и согласованность

### 20.1. Текущий мост

Authority: `dev.moduled.manager.bridge`.  
Permission: `dev.moduled.manager.permission.BRIDGE`, уровень `signature`.

Debug-хост и debug-менеджер используют общий сертификат. Production-модель подписи должна быть решена до выпуска патчера, иначе переподписанный TikTok не получит доступ к существующему мосту [S4]. Переход на иную модель IPC требует отдельного анализа доверия, не простого удаления permission.

### 20.2. Контракт

- Проверка вызывающего UID/сертификата и целевого пакета для каждой чувствительной операции.
- Нельзя выбирать произвольный файл путём из IPC-параметра.
- Большие DEX и отчёты передаются потоками/дескрипторами с лимитами, не одним огромным Binder payload.
- Снимок имеет поколение, список модулей, версии, хеши и связанный config snapshot.
- Читатель видит целиком старое или целиком новое поколение.
- Параллельное сохранение конфига и синхронизация не создают смешанный снимок.
- При повреждении нового поколения используется предыдущий целый снимок или безопасный отказ, не частично проверенный код.
- Сетевые операции и тяжёлая обработка не выполняются в критическом IPC-пути старта.

### 20.3. Хранение

Исполняемые файлы, доверенные ключи и runtime snapshots — во внутреннем хранилище соответствующего приложения. Общая папка пользователя — для обмена готовыми артефактами, не активное место исполнения.

Удаление приложения системой может удалить его private storage; это объясняется при резервном копировании. Экспорт конфигов не включает секретный ключ подписи без отдельного явного действия и защиты.

## 21. Интерфейс и доступность

### 21.1. MD3

Весь собственный UI вне TikTok, включая TModules, патчер, редактор, логи, доступы, тестовый хост и веб-каталог, следует MD3. Системные файловые диалоги, установщик APK и экраны Android не перекрашиваются приложением.

На Android применяются настоящие Material-компоненты: toolbar, cards, buttons, switches, text fields, dialogs, snackbar и роли типографики. Светлая/тёмная темы обязательны; динамические цвета используются там, где поддерживаются, с корректной базовой палитрой без них.

UI-библиотека подключается только к самостоятельным приложениям. Встраиваемый runtime и `module-api` не зависят от `standalone-ui` и MD3.

### 21.2. Экраны

1. Главная: состояние системы и доступ к основным разделам.
2. Патчер: входные файлы, совместимость, опции, выполнение и результат.
3. Модули: установленные пакеты, переключатели, ожидающий рестарт.
4. Карточка модуля: описание, версия, источник, доверие, config и действия.
5. Редактор: непреобразуемый текст, сохранить/отменить, статус несохранённых изменений.
6. Каталог: поиск, репозитории, карточки, загрузки и обновления.
7. Доступы: фактические системные разрешения отдельно от деклараций модулей.
8. Диагностика: runtime, снимок, safe mode, логи, экспорт и копирование.
9. Настройки: тема, приватность журналов, автокопирование, служебные сведения.

Конкретная навигация может объединять экраны, но не прячет обязательные функции.

### 21.3. Качество

- Проверка узкого экрана от 360 dp, увеличенного шрифта и TalkBack.
- Нажимаемые области ориентировочно не менее 48 dp.
- Корректные системные отступы, вырезы, клавиатура, поворот и edge-to-edge.
- Текст не перекрывается клавиатурой, ключевые действия доступны прокруткой.
- Значение состояния передаётся не одним цветом.
- Долгая операция имеет отмену или честное объяснение невозможности отменить текущую фазу.
- Нет фиктивных переключателей, пустых кнопок и сообщений об успехе до завершения операции.
- Основной язык первой поставки — русский; строки вынесены в ресурсы для последующей локализации.

## 22. Логи и приватность

Событие включает время, уровень, процесс, session ID, компонент/ID модуля и сообщение. Поддерживаются фильтрация, поиск, копирование и экспорт. Отчёт патчера отдельно содержит версии инструментов, входные хеши, план изменений и результаты проверок.

Проектный бюджет: runtime-журнал до 5 MiB на процесс с ротацией, до пяти crash-отчётов по 1 MiB каждый. Превышение отображается как усечение с возможностью найти полный доступный системный отчёт; значения уточняются после измерений. Логи не растут бесконечно и не переполняют диск.

По умолчанию собственный код не пишет пароли, токены, cookies, содержимое личных сообщений и конфиги целиком. Невозможно гарантировать это за произвольный DEX-модуль. Перед экспортом пользователь предупреждается, что отчёт может содержать личные данные. Автоматическая отправка логов и аналитика не включаются скрыто.

## 23. Нефункциональные требования

### 23.1. Производительность

- Нет ANR из-за I/O, распаковки или сетевых запросов на UI-потоке TModules.
- На согласованном эталонном устройстве p95 накладного времени runtime без модулей — первоначальный бюджет 200 ms, дополнительной PSS после стабилизации — 20 MiB.
- Эти числа — цели измерения, не достигнутые показатели прототипа. Методика, эталон и размер выборки фиксируются до приёмки; первоначально не менее 30 запусков на сценарий.
- Отдельно измеряются cold/warm start, первый импорт снимка, обычный запуск, safe mode и медленный/недоступный IPC.
- Накладные расходы модулей измеряются отдельно от пустого runtime.

### 23.2. Надёжность

- Атомарные сохранения состояния и установки пакетов.
- Восстановление после прерывания процесса и нехватки места.
- Понятный отказ при несовместимом backend вместо бесконечного crash loop.
- Валидация всех входов: архивы, descriptors, URI, IPC, конфиги и отчёты.
- Отсутствие обязательной сети для запуска уже установленной системы.

### 23.3. Сопровождение

Зависимости и их версии фиксируются, сторонние лицензии учитываются. Сборочная инструкция воспроизводима в документированной среде; битовая воспроизводимость подписанного APK — отдельная цель, не следствие наличия Gradle. Изменение API/формата сопровождается миграцией и тестами.

## 24. Этапы разработки и критерии выхода

### Этап 0. Устранение стартового краша — блокер

Результат: установленная причина B-001, минимальное исправление, доступный crash-отчёт менеджера и обновлённая тестовая сборка.

Приёмка:

- Получен реальный stack trace/эквивалентное подтверждение причины, а не предположение.
- TModules запускается после чистой установки и поверх текущей версии без очистки пользовательских данных.
- На устройстве, где возник сбой, выполнены не менее десяти последовательных запусков, включая cold start после завершения процесса.
- Проверены светлая/тёмная темы, открытие модулей, редактора и диалогов.
- Старые конфиги не потеряны, регрессия фиксируется автоматическим тестом там, где это возможно.

### Этап 1. Стабильная платформа на тестовом хосте

Результат: проверенные DEX-загрузка, Java-хук, текстовый конфиг, снимки, мост и safe mode.

Приёмка: пример действительно меняет результат метода на устройстве; отключение возвращает исходный результат после рестарта; три сбоя включают safe mode; повреждённые пакеты отклоняются; офлайн-запуск работает по документированному снимку.

### Этап 2. Первый настоящий патчер TikTok

Вход: конкретный пользовательский APK и согласованные Android/ABI.

Результат: минимальный поддерживаемый профиль, нативный pipeline патчинга, подпись и установочный результат.

Приёмка: исходник неизменён; результат проходит проверки, устанавливается по согласию пользователя; TikTok запускается без модулей; тестовый модуль меняет согласованный безопасный наблюдаемый участок; отключение и safe mode работают. Тестовый хост не засчитывается вместо этого этапа.

### Этап 3. Полноценный менеджер и репозитории

Результат: каталог, авторские descriptors, кеш, скачивание и подтверждаемое обновление; текстовые конфиги и экспорт; модель доверия.

Приёмка: установка из файла и репозитория, проверка хеша, отказ при подмене, офлайн-кеш, конфликты ID/ключей и сохранение config при обновлении проходят тесты. Подписи авторов проверяются до объявления источника «проверенным».

### Этап 4. Комплектные модули и доступы

Результат: модуль региона, необязательный внутренний менеджер, интерфейс доступов и поддерживаемые manifest-патчи.

Приёмка: оба комплектных модуля отключаются независимо; без внутреннего менеджера всё управляется через TModules; эффект региона измерен и ограничен описанием; manifest diff совпадает с выбранными изменениями; системные права не отображаются как выданные без подтверждения ОС.

### Этап 5. Расширенная совместимость

Результат: дополнительные версии TikTok, split pipeline, выбранные вспомогательные процессы, расширенная диагностика native-сбоев.

Приёмка проводится по каждой ячейке матрицы. Непроверенные версии не получают отметку «поддерживается».

### Этап 6. Необязательные расширения

Многодексовые модули, ресурсы/ассеты, `.so`, native hooks, файловые native-патчи, Shizuku, горячая конфигурация, дополнительные API и автоматизация публикации.

Каждое расширение требует отдельного формата/ADR, угроз, тестов и критериев отката. Оно не блокирует первую рабочую систему без таких возможностей.

## 25. Программа испытаний

### 25.1. Сборка и модульные проверки

- Чистая сборка в зафиксированной среде и существующие 13 core assertions.
- Статическая граница MD3/runtime, manifest и bridge permission.
- Негативные архивы: zip-slip, дубликаты, повреждённый CRC, огромная распаковка, неожиданные файлы, неверный DEX.
- Manifest: отсутствующие поля, неверные типы, дубли ключей, неподдерживаемая версия.
- Сбой установки на каждой фазе staging и сохранение предыдущей версии.
- Политика времени: третий сбой в окне, граница десяти минут, изменение системных часов, повторный event, явный сброс.

### 25.2. Инструментальные и ручные сценарии

**AT-01. Запуск менеджера:** чистая установка и обновление, запуск без интернета/TikTok, отсутствие падения.

**AT-02. DEX:** установка примера, подтверждение доверия, реальный вызов entrypoint и перехват метода.

**AT-03. Конфиг:** пустой файл, кириллица, emoji, BOM, пробелы, табы, CRLF/LF, отсутствие финального newline и файл у лимита — побайтовое сравнение после неизменённого сохранения.

**AT-04. Ошибки конфига:** неверный UTF-8, превышение байтового лимита, отсутствие места, отмена выхода и восстановление черновика.

**AT-05. Переключение:** изменение состояния, рестарт, фактическая загрузка/отсутствие загрузки; без рестарта UI не заявляет применение.

**AT-06. Обновление/удаление:** сохранение конфига, отказ при смене ключа без согласия, явное удаление данных.

**AT-07. Safe mode:** три подтверждённых сбоя блокируют все модули; обычный рестарт не снимает защёлку; force stop не увеличивает счётчик.

**AT-08. Отчёт:** сохранение до завершения, доступ после рестарта, ручное копирование, автокопирование при допустимых условиях и корректный fallback.

**AT-09. IPC:** чужой сертификат не получает доступ; отключённый менеджер не создаёт зависание; возраст offline-снимка виден.

**AT-10. Патчер:** неверный вход, неподдерживаемая версия, нехватка места, отмена, конфликт подписи, повторный патч и неизменность исходных файлов.

**AT-11. TikTok:** запуск без модулей, тестовый хук, выключение, модуль региона, safe mode на выбранной версии.

**AT-12. Опциональность:** сборка без внутреннего менеджера не содержит его функциональной зависимости; TModules полностью управляет системой.

**AT-13. Репозитории:** отсутствие иконок/скриншотов, неверный URL, timeout, недоступный автор, подмена архива и конфликт ID не ломают установленные пакеты.

**AT-14. UI:** темы, клавиатура, поворот, 360 dp, увеличенный шрифт, TalkBack, длинные названия, ошибки и пустые состояния.

**AT-15. ОС:** Android 9–10 с ограниченным crash detection, Android 11+ с exit history, Android 14+ с соответствующим target и read-only DEX; фактически проверенные версии фиксируются.

**AT-16. Расширения:** split/многопроцессность/native проверяются только после их реализации отдельными тестами и не помечаются «пройдено» из-за успешной сборки.

### 25.3. Общий критерий приёмки первой рабочей версии

Закрыт B-001; выполнены этапы 1–4 для одного согласованного APK/Android/ABI; доступны все базовые функции TModules; есть отдельный модуль региона и отключаемый внутренний менеджер; пройдены применимые AT-01–AT-15. Все исключения перечислены явно, без подмены реального TikTok тестовым хостом.

Наличие исходников функций без исполнения на устройстве не считается приёмкой.

## 26. Результаты поставки и работа с файлами

Для пользовательской проверки используется папка:

```text
/storage/emulated/0/tmoduled
```

В ней размещаются только нужные пользователю результаты:

- APK TModules;
- при необходимости тестовый хост с явной отметкой назначения;
- готовые ZIP-модули;
- инструкция проверки, список изменений и известные ограничения;
- это ТЗ;
- при необходимости отчёт проверки/контрольные суммы без секретов.

Не копировать туда Gradle cache, SDK, временные распаковки, лишние исходники и ключи подписи. Пользовательские файлы не удалять при обновлении поставки. Готовый изменённый TikTok сохранять только по выбранному пользователем пути; не публиковать чужой APK автоматически.

Исходники и рабочая документация остаются в проекте `tiktok-moduled`. Коммиты, отправка в GitHub, публикация Pages и загрузка релизов требуют отдельного действия; это ТЗ их не подразумевает.

## 27. Риски и меры

- **Обфускация TikTok:** адаптеры на конкретные версии, fingerprint и ранний отказ.
- **Несовместимый hook backend:** независимая матрица, тесты на ABI/Android, возможность смены backend без переписывания UI.
- **Вредоносный DEX:** предупреждение, доверенные источники и авторские подписи; не обещать sandbox.
- **Несовместимая подпись TikTok:** явный план установки, сохранение ключа и предупреждение до риска удаления данных.
- **Менеджер падает:** отдельная диагностика и минимальный путь восстановления, B-001 закрывается первым.
- **Менеджер недоступен:** локальный целый snapshot, видимое устаревание, локальный safe mode.
- **Сбой внутри native/раннего кода:** покрытие по ОС, ранняя защита, отдельные тесты; не считать Java handler универсальным.
- **Системный запрет рестарта/буфера:** best effort с сохранённым отчётом и ручным действием.
- **Утечка через логи:** минимизация собственных сообщений, ограничение хранения, предупреждение перед экспортом.
- **Недоступный GitHub/CDN:** кеш и установка из файла; runtime не зависит от сайта.
- **Несовместимые пользовательские конфиги:** платформа сохраняет текст, ошибки синтаксиса объясняет автор модуля.
- **Изменение правил распространения:** канал доставки и сторонние лицензии проверяются перед публикацией; автоматического обещания совместимости с политиками магазинов нет.

## 28. Рабочие предположения и решения до реализации

Документ не требует ответа на эти пункты для своего использования, но они должны быть закрыты на соответствующем этапе:

1. Выбрать конкретный входной APK TikTok, Android и ABI для первого интеграционного теста.
2. Получить воспроизведение/лог B-001 и установить реальную причину стартового падения.
3. Зафиксировать production-модель подписи менеджера, хоста и безопасного хранения ключей.
4. Выбрать фактическую точку bootstrap и минимальный наблюдаемый тестовый хук TikTok.
5. Согласовать версионирование новых полей descriptor и будущего архива v2.
6. Зафиксировать алгоритм подписи авторских пакетов и процедуру доверия/ротации ключей.
7. Определить проверяемый локальный эффект модуля региона без обещания серверного обхода.
8. Установить адрес и правила модерации каталога, затем отдельно опубликовать GitHub Pages.
9. Выбрать лицензию собственного кода; текущие сторонние уведомления не заменяют её.
10. Выбрать эталонное устройство и методику измерений производительности.

Профессиональные значения по умолчанию этого ТЗ: новые сторонние модули выключены до согласия, обновления ручные, root/Shizuku не обязательны, доступ в интернет при запуске runtime не нужен, config сохраняется без преобразований, safe mode выключает все модули.

## 30. Итоговое определение продукта

**TModules — нативный MD3-патчер и независимый менеджер доверенных DEX-модулей для TikTok.** Он устанавливает платформу, управляет модулями и их непреобразуемыми текстовыми конфигами, подключает авторские репозитории, показывает реальные доступы и помогает восстановиться после сбоев. Регион и внутренний менеджер — отдельные модули. Свобода кода максимальна внутри реальных возможностей процесса Android, без фиктивного обещания изоляции, root или универсальной совместимости.
